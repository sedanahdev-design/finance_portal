# منصة القسم المالي (Finance Portal)

منصة ويب داخلية لأتمتة عمليات القسم المالي المتكررة. يرفع الموظف ملف إكسل، تعالجه المنصة وفق منطق كل عملية، ثم تعرض ملخصاً واضحاً وتتيح تنزيل النتيجة النهائية كملف إكسل منسّق. المنصة مبنية على إطار Django مع قاعدة بيانات PostgreSQL، وتدعم صلاحيات دقيقة لكل مستخدم على كل وحدة على حدة.

---

## ما الذي تقدّمه المنصة

تجمع المنصة تسع وحدات عمل مستقلة تحت واجهة عربية واحدة، بالإضافة إلى طبقة أساسية مشتركة تدير الدخول والمستخدمين والصلاحيات وسجل التدقيق.

| # | الوحدة | الوظيفة باختصار |
|---|--------|-----------------|
| 1 | مطابقة هبة – سدانة | مطابقة دفتري أستاذ لطرفين لنفس العلاقة المالية، وإبراز الحركات المتطابقة والفروقات وأسبابها |
| 2أ | عمولات المندوبين | احتساب عمولة كل مندوب على صافي مبيعاته، مع عمولات فرعية (معقمات، نسبة الجهات الشريكة) وتفصيل حسب المورد والشركة |
| 2ب | عمولة تحصيل الموزعين الداخليين | احتساب عمولة التحصيل لكل موزع وفق فئته وعدد المشاركين في الحركة، مع تفصيل حالات التحصيل والمرتجعات |
| 3 | تنظيف داتا | توحيد وتنقية بيانات المبيعات والمرتجعات ودفاتر الذمم وإخراجها بصيغة جاهزة للاستخدام |
| 4 | مطابقة جرد الضريبة | توزيع الكميات على الصيدليات ضمن سقف مسموح لكل مادة، باختيار أفضل مزيج ممكن دون تجاوز السقف |
| 6 | مطابقة دواك | مطابقة على مستوى الصيدلية وعلى مستوى الحركة الفردية بين ملفات دواك وكشف حساب هبة |
| 7 | فصل كشف الحساب (ليرة / دولار) | فصل حركات كشف الحساب حسب عملتها الأصلية واستخراج القيمة الحقيقية لكل حركة |
| 8 | تعويضات فيتا فارما | احتساب قيمة المطالبة لكل مادة وصيدلية وعرض مفرق وفق منهجية العروض المميزة والهدايا |
| 9 | عمولات الموزعين الخارجيين | احتساب رصيد وعمولة كل موزع خارجي وفق معادلة المرتجعات والكشوفات |

كل وحدة اختُبر منطقها الحسابي على ملفات حقيقية. تظهر درجة اليقين ومصدر التحقق لكل وحدة داخل واجهتها نفسها ضمن صناديق تنبيه، وتتفاوت بحسب توفّر بيانات مرجعية جاهزة للمقارنة الرقمية. بعض الوحدات مطابقة رقمياً بالكامل لمرجع معتمد، وبعضها ضمن هامش صغير موثّق سببه.

## المتطلبات التقنية

- **لغة التطوير:** Python 3.11
- **الإطار:** Django 5.2
- **قاعدة البيانات:** PostgreSQL 16
- **خادم التطبيق:** Gunicorn
- **الملفات الثابتة:** WhiteNoise
- **معالجة الإكسل:** openpyxl
- **الواجهة:** Bootstrap RTL وأيقونات Bootstrap وخط Cairo، جميعها محمّلة محلياً دون أي اعتماد على شبكات توصيل خارجية

جميع الحسابات المالية داخلياً بنوع `Decimal` وليس أرقاماً عشرية عائمة، ولا يدخل أي ذكاء اصطناعي في أي منطق حسابي، فكل نتيجة قابلة للتفسير والتتبع الكامل.

## التشغيل عبر Docker (الطريقة الموصى بها)

المشروع جاهز للتشغيل الكامل عبر Docker Compose، ويشمل ذلك تطبيق Django وقاعدة بيانات PostgreSQL معاً.

1. انسخ ملف `.env.example` إلى ملف باسم `.env`، ثم عدّل القيم داخله، وعلى وجه الخصوص المفتاح السري لـ Django وكلمة سر قاعدة البيانات.
2. شغّل الأمر الذي يبني الصور ويرفع الحاويات في الخلفية (`docker compose up --build -d`).
3. عند الحاجة إلى مستخدم مشرف ولم تُضبط بياناته مسبقاً في `.env`، أنشئه يدوياً عبر أمر `createsuperuser` داخل حاوية `web`.

يفتح الموقع على المنفذ **8010** من الجهاز المضيف (بدلاً من 8000 الافتراضي، تفادياً للتعارض مع مشاريع أخرى)، ويمكن تغيير هذا المنفذ عبر المتغير `WEB_PORT` في `.env`.

عند كل إقلاع تنتظر حاوية `web` جاهزية قاعدة البيانات، ثم تطبّق الترحيلات وتجمع الملفات الثابتة تلقائياً، ثم تشغّل الخادم عبر Gunicorn. تُحفظ الملفات المرفوعة والنتائج المُصدَّرة في وحدة تخزين دائمة، فلا تُفقد بين عمليات إعادة التشغيل.

### تجربة سريعة عبر نفق Cloudflare

يوفّر المشروع دعماً مدمجاً لأنفاق Cloudflare السريعة (مجانية وبلا حساب) لتجربة الموقع من أي مكان دون نشر فعلي. يُشغَّل النفق عبر تفعيل ملف تعريف `tunnel` في Docker Compose، ثم يُتابَع سجل حاوية `cloudflared` حتى يظهر فيه رابط بصيغة نطاق فرعي على `trycloudflare.com`؛ هذا هو رابط الموقع المؤقت، ويعمل تسجيل الدخول عبره دون أي إعداد إضافي لأن نطاق `trycloudflare.com` موثوق مسبقاً في إعدادات المشروع.

هذا الرابط عشوائي ومؤقت ويتغيّر مع كل إعادة تشغيل للنفق، فهو مناسب للتجربة فقط لا للاستخدام الدائم.

## التشغيل محلياً دون Docker

1. تأكد من أن خدمة PostgreSQL تعمل على الجهاز.
2. ثبّت المتطلبات المذكورة في `requirements.txt`.
3. طبّق ترحيلات قاعدة البيانات عبر أمر `migrate` (أول مرة فقط، وبعد أي تعديل على النماذج).
4. شغّل خادم التطوير على المنفذ الذي تريده، ثم افتح المتصفح على العنوان المحلي المقابل له.

القيم الافتراضية لقاعدة البيانات محلياً: الاسم `finance_portal`، المستخدم `finance_admin`، وكلمة المرور معرّفة في `finance_portal/settings.py`. يُفضّل تمرير هذه القيم عبر متغيرات البيئة `DB_*` عند أي استخدام فعلي.

## الدخول وإدارة المستخدمين

تُنشأ حسابات تجريبية للتطوير فقط، ويجب تغيير كلمات مرورها قبل أي استخدام حقيقي:

| اسم المستخدم | الدور |
|---|---|
| `supervisor` | مشرف القسم، صلاحية كاملة على كل الوحدات |
| `staff1` | موظف، ممنوح صلاحية وحدة واحدة كتجربة |
| `staff2` و `staff3` | موظفان دون صلاحيات بعد |

كلمات المرور التجريبية موثّقة داخلياً لفريق التطوير.

يستطيع مشرف القسم من صفحة **المستخدمون والصلاحيات** إنشاء المستخدمين وتعديلهم وضبط وصول كل مستخدم إلى كل وحدة على ثلاثة مستويات (عرض، رفع وتشغيل، تصدير) دون أي تعديل في الكود.

لوحة إدارة Django التقنية متاحة على المسار `/django-admin/` (وليس `/admin/`) لحسابات المشرفين فقط، ورابطها موجود في القائمة الجانبية تحت «إدارة النظام». الطريقة الموصى بها للإدارة اليومية هي صفحة «المستخدمون والصلاحيات» الخاصة بالمنصة.

## النشر على نطاق حقيقي

عند تشغيل المنصة خلف نطاق ثابت خاص بكم عبر بروكسي عكسي أو نفق مسمّى (Cloudflare أو غيره)، يجب تحديد المتغير `DJANGO_CSRF_TRUSTED_ORIGINS` في `.env` بالرابط الكامل الذي يستخدمه المستخدمون فعلياً مع بادئة `https://`؛ وإلا فسيفشل تسجيل الدخول برسالة «CSRF verification failed». السبب أن Django لا يثق تلقائياً بأي نطاق جديد، ولا يعلم أن الاتصال جرى عبر HTTPS ما دام البروكسي هو من ينهي شهادة الأمان. هذا الإعداد مع رأس البروكسي المُفعَّل مسبقاً في الإعدادات يحلّان الأمرين معاً. بعد أي تعديل على `.env` يجب إعادة تشغيل الحاويات.

قبل النشر على الإنترنت فعلياً، يعرض أمر `check --deploy` في Django قائمة تنبيهات أمان قياسية يجب تفعيلها بعد وضع الموقع خلف HTTPS حقيقي: مفتاح سري عشوائي طويل بدل القيمة الافتراضية، ثم تفعيل إعادة التوجيه الإجباري إلى HTTPS وكوكيز الجلسة والحماية من التزوير الآمنة وسياسة HSTS. لم تُفعَّل هذه الإعدادات افتراضياً لأنها تمنع الوصول عبر HTTP العادي كما في التشغيل المحلي دون شهادة.

## هيكلية المشروع

```
finance_portal/
  core/                     الطبقة الأساسية: المستخدمون، الأدوار، الصلاحيات لكل وحدة، سجل التدقيق، القالب العام
  reconciliation_hs/        1) مطابقة هبة – سدانة
  commissions/              2أ) عمولات المندوبين
  distributor_commissions/  2ب) عمولة تحصيل الموزعين الداخليين
  data_cleaning/            3) تنظيف داتا
  tax_inventory/            4) مطابقة جرد الضريبة
  dawak_compare/            6) مطابقة دواك
  account_statement/        7) فصل كشف الحساب (ليرة / دولار)
  compensation/             8) تعويضات فيتا فارما
  external_commissions/     9) عمولات الموزعين الخارجيين
  static/                   ملفات الواجهة المحلية (Bootstrap RTL، الأيقونات، خط Cairo)
  templates/base.html       القالب العام: القائمة الجانبية والشريط العلوي والألوان
  Dockerfile, docker-compose.yml, docker/entrypoint.sh, .env.example
```

كل وحدة مبنية بالنمط نفسه لتسهيل القراءة والصيانة:

- `engine.py` — منطق العمل الحسابي المستقل القابل للاختبار بمعزل عن الويب.
- `excel_export.py` — توليد ملف الإكسل النهائي بتنسيق واضح متعدد الصفحات.
- `models.py` — نموذج يحفظ ملخص كل عملية تشغيل والملف الناتج.
- `forms.py` و `views.py` — دورة الرفع ثم التشغيل ثم عرض النتيجة ثم التنزيل.
- `templates/<app>/` — صفحتا الإدخال والنتيجة الخاصتان بالوحدة.

## الأمان والتدقيق

- سجل تدقيق يسجّل كل تسجيل دخول ورفع ملف وتشغيل عملية وتنزيل نتيجة، مع اسم المستخدم والوقت وعنوان الـ IP.
- صلاحيات دقيقة لكل مستخدم على كل وحدة، بثلاثة مستويات منفصلة.
- جميع الحسابات المالية بنوع `Decimal` لتفادي أخطاء التقريب.
- لا يدخل أي ذكاء اصطناعي في أي منطق حسابي؛ كل نتيجة قابلة للتفسير والتتبع.
